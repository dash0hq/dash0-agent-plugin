# copilot/session

What one GitHub Copilot CLI turn looks like in Dash0 once it ends: where its numbers come from,
where its tool spans come from, and the attribute surface they carry. Two turns are
[../turns](../turns/README.md); delegation is [../subagents](../subagents/README.md).

Every spec here needs no flag beyond the driver's defaults. Regenerated by `/qa-author`, not
appended to, so a gap stays visible.

| Invariant | Spec | Status |
| --- | --- | --- |
| A turn's `chat` span carries usage summed from the native-OTel file, and none when there is no file | [turn-usage-comes-from-the-native-otel-file](turn-usage-comes-from-the-native-otel-file.md) | active, passing |
| Tool spans come from the OTel file with real durations, not from the tool hooks | [tool-spans-come-from-the-otel-file](tool-spans-come-from-the-otel-file.md) | active, passing |
| No span carries an attribute outside the contract in `DEVELOPMENT.md`, and Copilot's own cost figure is not exported at all | [copilot-span-carries-no-undeclared-attribute](copilot-span-carries-no-undeclared-attribute.md) | active, passing **for prompt mode**. Was broken until 2026-08-28: `stopReason` shipped raw on every `chat` span, `github.copilot.cost` shipped at all, `dash0.gen_ai.tool.task.name` shipped as a custom key where a standard one belonged, and `traceparent` shipped on every interactive session's chat span — which this spec cannot see, since the driver runs prompt mode |

## Not written, with the reason

| Invariant | Why not |
| --- | --- |
| A failed tool call sets the span status | The input does not exist yet on this runtime. Measured 2026-08-28: `exit 3` gives a `postToolUse` payload with `"resultType": "success"` and a native span with no error status, so Copilot treats a command that ran as a tool that worked. A spec needs a tool that fails at the tool level, and none has been found that fails on demand |
| An MCP call names its server and the span carries the stripped tool name | No MCP fixture reaches the throwaway home yet, and the organization policy on this account disables third-party MCP servers outright — the session log says so on every run. `internal/pipeline`'s normalization is asserted by unit tests meanwhile |
| The `chat` span carries the turn's response text | Depends on `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`, which the driver sets and the launch function sets. Worth writing; it is `gen_ai.output.messages` sourced from the OTel chat span rather than from a hook, which is a real difference from the other runtimes |
| No span has a parent that no other span carries | Now a check inside `qa-compare.py`, running on every comparison in every runtime. A spec would assert what the tool already asserts everywhere |
| Line counts on a file edit | The plugin does not emit them here, deliberately: Copilot's `apply_patch` carries no `structuredPatch`, only raw patch text. `copilot/README.md` records it as a known limitation, so there is nothing to assert until a patch-text extractor exists |

## Why "no usage" is a real case and not a broken run

Native OpenTelemetry is off by default in Copilot, and the plugin cannot turn it on: Copilot passes
no launch environment to hook processes. In production the `dash0-configure` skill installs a shell
function that enables it; a user who skips that step gets a working plugin that emits one `chat`
span per turn **with no usage and no tool spans**. That degradation is documented behaviour, so
`QA_COPILOT_NO_OTEL=1` drives it and the spec above asserts it rather than treating it as a failure.

It also changes how a report must be read: with no file, the second channel reports *nothing*
rather than zero, `qa-compare.py` prints `-` in its column and compares nothing against it, and the
run rests on the hook record alone.
