# codex/skills

Whether a skill Codex loaded is observable, and whether the count of them can be trusted.
[../session](../session/README.md) is one session's spans and numbers;
[../subagents](../subagents/README.md) is delegation.

Every spec here needs `QA_CODEX_SKILL=1`, which installs
[../../../skill-fixture/qa-echo](../../../skill-fixture/qa-echo/SKILL.md) into the throwaway home.
Regenerated by `/qa-author`, not appended to, so a gap stays visible.

| Invariant | Spec | Status |
| --- | --- | --- |
| A loaded skill is named on the turn's `chat` span, with the route that chose it, and a turn that only *has* skills available carries nothing | [skill-invocation-is-attributed-by-either-route](skill-invocation-is-attributed-by-either-route.md) | draft, passing. The product did not attribute Codex skills at all until 2026-08-26 |
| A skill the model chooses unprompted is attributed to the model | — | not written; the input cannot be forced. Dropping the `$mention` may make the model load the skill or may make it do the work itself, so the run is not repeatable by construction. The assertion is in the spec's tolerance for when it does happen |
| A skill that fails, or is interrupted, is still named | — | not written. A Codex tool failure is invisible to the plugin at all — no failure hook, no exit code in the payload or the rollout — so there is nothing to distinguish this from the passing case |
| Two skills in one turn are both reported | — | not written, and today it cannot pass: one attribute names one skill, and the reader takes the last. Worth revisiting only if a real session does it |

## Why Codex needs its own arm of this

Claude Code has a `Skill` tool for the model route and expands a slash command for the person's,
and the plugin reads the second from the transcript. **Codex has no `Skill` tool for either
route.** It loads a skill by injecting it into the conversation, so both routes land on the turn's
`chat` span and both are read from the rollout. A count compared across the two runtimes will not
line up by span type, only by attribute — which is the point of `skill.name` being the same key in
both.

## The trap this area exists to control for

A session with any skill installed carries `<skills_instructions>` — the catalogue of everything
available — in **every** turn. It is a developer message and it says nothing about what was used.
Reading it as usage would attribute a skill to every turn of every session that has one, and no
single-turn run could tell. That is why the spec here spends a second turn proving the negative.
