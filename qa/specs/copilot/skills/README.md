# copilot/skills

Whether a skill Copilot loaded is observable, and on which span. [../session](../session/README.md)
is one turn's spans and numbers; [../subagents](../subagents/README.md) is delegation.

Every spec here needs `QA_COPILOT_SKILL=1`, which copies
[../../../skill-fixture/qa-echo](../../../skill-fixture/qa-echo/SKILL.md) into
`$COPILOT_HOME/skills/` in the throwaway home — the personal-skills location Copilot documents.
Regenerated by `/qa-author`, not appended to, so a gap stays visible.

| Invariant | Spec | Status |
| --- | --- | --- |
| A skill the model invokes is named on the `skill` tool span, with the route that chose it | [skill-invocation-is-named-on-the-tool-span](skill-invocation-is-named-on-the-tool-span.md) | active, passing |

## Not written, with the reason

| Invariant | Why not |
| --- | --- |
| A skill invoked by a person's command is attributed to the command | Copilot has no slash-command route into a personal skill that reaches the plugin. `dash0.gen_ai.tool.skill.source` is therefore always `model` here, and a spec for the other value would assert an input that does not exist |
| A turn that only *has* skills available carries nothing | Cheap to add and worth adding. Copilot lists the available skills in `github.copilot.context.skills` on its own `invoke_agent` span, which the plugin does not read, so the trap the Codex arm controls for does not exist in the same form — but proving the negative is still the way to know that |
| Two skills in one turn are both reported | One attribute names one skill and each invocation is its own tool call, so on this runtime two skills would be two spans rather than a lost second name. Different question from the Codex one, and it needs a prompt that reliably loads two |
| A skill that fails is still named | The same tool-level failure gap the session area records |

## Why Copilot's arm of this is the simplest of the three

Claude Code has a `Skill` tool for the model route and expands a slash command for the person's,
and the plugin reads the second from the transcript. Codex has neither, and injects the skill into
the conversation, so both its routes land on the turn's `chat` span.

**Copilot has one route and it is a tool call.** The model calls a tool named `skill`, the native
`execute_tool` span carries `github.copilot.tool.parameters.skill_name`, and the plugin maps that to
`dash0.gen_ai.tool.skill.name` on the tool span through the same extractor the other runtimes use.
Nothing lands on the `chat` span.

That matters when carrying a spec over: `DEVELOPMENT.md` scopes the chat-span route to Claude and
Codex, and a Copilot spec that looks for the skill name there will find nothing and report a defect
that is not one. Measured 2026-08-28 on `qa/runs/probe-skill`: the `execute_tool skill` span carried
`dash0.gen_ai.tool.skill.name` and `.source = model`, and the turn's `chat` span carried neither.
