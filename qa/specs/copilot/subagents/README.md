# copilot/subagents

What delegation looks like in Dash0 when a Copilot turn spawns a sub-agent through the `task` tool.
One turn is [../session](../session/README.md); two turns are [../turns](../turns/README.md).

Every spec here needs a prompt the model actually delegates on, and no flag: Copilot's `task` tool
is available by default, unlike Codex's sub-agents. Regenerated by `/qa-author`, not appended to, so
a gap stays visible.

| Invariant | Spec | Status |
| --- | --- | --- |
| A sub-agent gets its own `invoke_agent` span under the tool that spawned it, its tools nest beneath that, and its hook session mints nothing | [subagent-gets-its-own-invoke-agent-span](subagent-gets-its-own-invoke-agent-span.md) | active, passing. The span shape changed on 2026-08-28: the native `invoke_agent` layer used to be collapsed and the sub-agent's identity put on a `dash0.*` key of the tool span, which no backend feature reads |

## Not written, with the reason

| Invariant | Why not |
| --- | --- |
| A sub-agent's tokens are attributed to the sub-agent | The product does not do this and says so: attribution is flat, and a sub-agent's `chat` spans fold into the parent turn's total. `copilot/README.md` records it as a limitation. The `invoke_agent` span deliberately carries no usage for that reason — repeating the parent's tokens there would double any sum across the trace |
| Two sub-agents in one turn are told apart | The same mechanism as one, plus a prompt the model reliably splits in two. Worth writing once such a prompt exists; `gen_ai.agent.id` is what carries the distinction, since it is the spawning call id rather than the agent kind |
| A reused sub-agent keeps producing spans | Copilot has no equivalent of the reusable Codex agent this asks about — each `task` call is its own tool call, its own `call_` session, and its own `invoke_agent` span |
| A failed sub-agent is marked | No way to make one fail on demand, and the same tool-level failure gap the session area records |

## How a Copilot sub-agent reaches Dash0, and what the hooks cannot say

The other two runtimes get a hook that names the sub-agent and links it to its parent. **Copilot
gives neither.** A sub-agent fires a hook lifecycle of its own, under its own session id, and
nothing in those payloads links back to the parent conversation — verified against captured
payloads.

**It is a partial lifecycle, and that is what the plugin keys on.** A sub-agent receives
`userPromptSubmitted`, any `postToolUse`, and `agentStop`, and never `sessionStart` or
`sessionEnd`; only the session a person started gets those. The id is not usable for this:
`copilot -p` names a sub-agent session `call_<toolCallId>`, which the normalizer drops on the
prefix, but an interactive session gives it a plain UUID. So the entrypoint drops any session that
reaches a Stop having never had a SessionStart, rather than mint a standalone, token-less
"conversation" per sub-agent.

Everything real arrives through the native-OTel file instead, which describes the sub-agent
properly. The plugin reproduces that tree, collapsing only the layers it emits nothing for — the
native `chat` spans, and the turn's root `invoke_agent`, which the pipeline's own chat span already
represents:

```
chat  →  execute_tool task  →  invoke_agent task  →  execute_tool bash
```

Same shape as Claude and Codex, so a count compared across runtimes lines up by span type. The
`invoke_agent` span carries `gen_ai.agent.name` (the agent kind, e.g. `task`) and `gen_ai.agent.id`
— the spawning `call_…` id, which is unique per invocation and, under `copilot -p`, also names
that sub-agent's own hook session. Interactively that hook session is a plain UUID, so the join is
prompt-mode only. The native span's own `gen_ai.agent.id` is `builtin:task`, shared
by every sub-agent of that kind, and is deliberately not used.

## The divergence this area exists to explain

On a delegating turn, Copilot's own per-turn roll-up disagrees with the sum of that turn's `chat`
spans, and `qa-compare.py` prints the gap. **That is expected.** The roll-up on the top-level
`invoke_agent` span excludes the sub-agent's own round-trips; the plugin's flat attribution includes
them. Measured 2026-08-28 on `qa/runs/probe-subagent`: 29563/232 from the roll-up against 52038/298
from the chat spans, and Dash0 correctly carries the latter. It is Copilot's arithmetic, not the
plugin's, and it is not a finding.
